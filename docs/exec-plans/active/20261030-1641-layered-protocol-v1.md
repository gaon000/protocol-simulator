# 계층별 프로토콜 시뮬레이터 v1 구현 계획

상태: In Progress
작성일: 2026-10-30
종료일: 미종료
현재 단계: P0 master 반영·원격 push, P1 코어 구현·전체 로컬 검사 완료. 다음 단계 P2이며 P2~P7은 미시작.

이 문서는 [ExecPlan 운영 규칙](../index.md)을 따른다. 최초 요청은 설계를 문서화하고 구현 계획을 작성하는 범위였으며 애플리케이션 구현·패키지 설치·배포는 수행하지 않았다. 문서의 커밋·push는 이후 사용자의 별도 요청 범위를 따른다. 사용자가 P0 구현을 요청하고 React·React DOM의 production dependency 추가를 승인했다. 이후 신규 production dependency도 추가 전에 사용자 확인을 받는다.

## Purpose / Big Picture

사용자가 응용 또는 전송 계층의 프로토콜을 정의하고 하위 통신 환경을 바꾸어 가상 참여자 A·B 사이에서 실행할 수 있게 한다. 기존 예제에서 메시지·규칙·상태와 환경의 영향을 이해하고, 사본을 편집해 동일한 흐름으로 검증할 수 있어야 한다.

완료 시 관찰할 수 있는 핵심 결과는 다음과 같다.

1. 응용 프로토콜이 스트림 수신 청크의 분할·합치기에 관계없이 메시지를 해석한다.
2. 전송 프로토콜이 정상·손실 환경에서 타이머·재전송·중복 제거를 수행하며 원인을 기록한다.
3. 같은 snapshot·seed·엔진 버전으로 재실행한 의미적 이벤트 기록이 동일하다.
4. 사용자가 정의·환경·시나리오를 화면에서 편집하고, 실행 이벤트에서 데이터·규칙·상태 변화로 이동한다.
5. 로컬 저장·내보내기·가져오기 후 실험을 재개하고 과거 결과를 당시 설정으로 확인한다.

실제 네트워크, 여러 사용자 계층의 연결 실행, 전체 TCP/HTTP 호환성, 임의 바이너리 코덱, 계정·서버·배포는 범위 밖이다.

## Surprises & Discoveries

- 2026-10-30 문서 작성 시작 시 Git은 커밋이 없는 저장소였고 브랜치는 `codex/apply-ai-dev-template`였다. 당시 untracked 문서를 보존하며 작업했다. 이후 브랜치·커밋 상태는 작업 시작 시 Git에서 다시 확인한다.
- 템플릿 도입 이후 제품 방향이 합의됐다. 현재 구조 문서의 미구현 사실은 유지하고 목적·요구사항 진입점만 갱신한다.
- TCP의 바이트 스트림과 사용자 정의 메시지·논리 패킷은 다른 전달 계약이다. 계층 이름만으로 서비스를 선택하면 응용/전송 동작을 잘못 검증할 수 있어 별도의 호환성 검사가 필요하다.
- 검증 통과, 프로토콜의 종료 상태, 실행 엔진의 정상 종료는 다르다. 예상한 timeout을 관찰한 경우와 자원 한도로 관찰을 중단한 경우를 구분해야 한다.

## Plan of Work

진행 순서는 P0 → P1 → P2 → P3 → P4 → P5 → P6 → P7이다. P3에서 이상적인 환경으로 편집·실행의 작은 전체 흐름을 먼저 연결하고 P4 이후 장애·예제·저장으로 넓힌다. 각 단계는 관련 테스트와 문서 갱신까지 끝나야 완료로 표시한다. 예상 소요 시간은 아직 산정하지 않는다.

### P0 — 개발 기반과 실행 세부 계약

의존: 구현 요청과 도구·의존성 선택.

변경 위치: 향후 루트 manifest·lockfile·Node 버전 설정·strict TypeScript 설정·검사 도구, 최소 UI 진입점, `docs/development.md`, 이 문서의 결정 로그.

1. 현재 Node·pnpm 환경을 다시 확인한다. Node v22 이상을 기준으로 고정 버전을 선택하고 없으면 nvm을 확인한다. 과거 조사된 설치 상태만 믿지 않는다.
2. UI 프레임워크·빌드 도구·테스트 도구를 선정한다. production dependency 목록·목적을 사용자에게 확인한 뒤 추가한다. 코어 테스트는 DOM 없이 실행한다.
3. manifest·lockfile과 strict TypeScript, 타입 검사·단위 테스트·UI 테스트·문서 검사·빌드 명령을 구성한다. 실행하지 않은 스크립트는 통과로 기록하지 않는다.
4. 서비스 포트와 snapshot JSON 형태를 작은 fixture로 검토한다. 같은 시각 전달/timeout 처리, 명시적 무시·규칙 충돌, seed 알고리즘과 환경 처리 순서, 기본 상한을 확정한다.
5. 최소 웹 작업 공간을 열 수 있게 하고 이후 단계에서 쓸 검사 명령을 개발 문서에 실제 값으로 기록한다.

검증: 최소 화면 기동과 빌드, strict 타입 오류 검출, 실제 테스트 한 개 이상 수집·실행, 문서 링크 검사. 빈 테스트 실행을 통과로 보지 않는다.

완료 조건: 실제 명령으로 재현 가능한 기반이 있고, 주요 결정과 의존성 확인 여부가 기록되어 P1을 시작할 수 있다. P0 구현과 개별 검증은 완료했으며 실제 결과는 아래 검증 기록을 따른다.

### P1 — 정의 모델·검사·코덱

의존: P0.

변경 위치: 향후 `src/domain/`, `src/codecs/`, `tests/unit/`.

1. ProtocolDefinition·EnvironmentDefinition·ScenarioDefinition·Experiment·RunSnapshot·EventTrace·RunResult의 버전 있는 모델을 정의한다.
2. 필드 타입·기본값·범위, 상태·변수·규칙 참조, 양쪽 정의의 서비스 호환성과 기대 조건을 검증한다. 초안 저장 가능 여부와 실행 유효성을 구분한다.
3. JSON Lines stream, JSON datagram, 구조화된 논리 패킷 코덱을 구현한다. 상태·규칙·패킷·타이머·변수는 안정적인 ID로 연결한다.
4. 오류에 정의 위치와 원인 참조를 포함해 나중에 UI가 해당 폼으로 이동할 수 있게 한다.

검증: 유효/무효 모델과 서비스 불일치, 잘못된 참조·타입·범위, UTF-8를 포함한 모든 바이트 분할 위치, 여러 메시지 합쳐 읽기, 잘못된 JSON, 미완성 EOF, 크기 상한. 도구가 자동으로 구조화된 JSON을 전달하는 것만으로 스트림 검증을 대체하지 않는다.

완료 조건: 고정 fixture의 encode/decode와 정의 오류 위치를 DOM 없이 재현한다.

구현 결과: [P1 계약](../../design-docs/p1-models-codecs.md), [완전한 모델 fixture](../../../tests/fixtures/protocol-models.ts), 모델/코덱 단위 테스트와 snapshot 왕복 통합 테스트를 추가했다. 실제 이벤트 실행과 편집 화면 연결은 이 단계의 완료 조건에 포함하지 않는다.

### P2 — 결정적 엔진·타이머·기록

의존: P1.

변경 위치: 향후 `src/engine/`, `src/environments/`, 코어용 `src/application/`, `tests/unit/`, `tests/integration/`.

1. 가상 시계·안정적인 이벤트 정렬·seed 기반 난수·실행 상한을 구현한다. 환경은 큐·난수를 주입받는다.
2. 참여자별 상태·변수·버퍼·타이머와 선언형 규칙을 실행한다. 전송·수신·파싱·상위 전달을 별도 이벤트로 기록한다.
3. 손실 없는 이상적 stream/datagram 환경과 Ping/Pong fixture를 연결한다.
4. 실행·일시정지·단계 실행·초기화·중단, immutable snapshot과 runId fencing을 구현한다.
5. 기대 조건의 pass/fail/undetermined와 엔진의 terminal 상태를 분리한다. 관찰 기간과 큐 소진을 처리한다.

검증: 동일 snapshot 재실행 기록 비교, 정확히 기한에 도착하는 응답, 타이머 취소·재시작과 늦은 만료, 동일 정의 인스턴스 간 격리, 충돌/무일치 규칙, 0ms 루프·기록 상한, 정지 후 이전 run 결과 무시. 실제 시간 대기는 사용하지 않는다.

완료 조건: Ping/Pong의 정상·기대된 timeout·제한 중단을 서로 다른 결과로 재현하고 전체 실행과 단계 실행의 의미적 기록이 일치한다.

### P3 — 편집부터 실행까지 첫 화면 연결

의존: P2.

변경 위치: 향후 `src/ui/`, `src/application/`, UI·통합 테스트.

1. 시작 화면과 실험 구성·프로토콜·통신 환경·시나리오/검증·실행의 작업 공간을 연결한다. 이 단계의 환경 선택은 구현된 이상적 모델만 노출한다.
2. 메시지 필드, 상태·변수, 규칙, 최초 입력과 기대 조건을 실제 초안에 편집한다. 고정 시퀀스를 보여주는 mock으로 구현 완료를 대신하지 않는다.
3. 실행 시 snapshot을 만들고 실제 엔진 기록으로 시퀀스·상태·오른쪽 상세·하단 진단을 갱신한다.
4. 오류에서 편집 위치, 실행 이벤트에서 원인 규칙·상태 변화로 이동한다. 초안과 실행 버전 차이를 표시한다.

검증: 화면에서 Ping의 필드/응답 조건을 바꾸면 실제 기록과 검증 결과가 바뀜, 구조 오류 시 실행 차단, 키보드 폼 편집, 전체/단계/정지/초기화, 이벤트 선택과 근거 연결.

완료 조건: 사용자가 화면에서 새 Ping/Pong 실험을 정의해 이상적 환경에서 실행하고 기대 결과와 원인을 확인한다. 새로고침 보존은 P6 전까지 미지원으로 표시한다.

### P4 — 하위 환경 장애와 재전송

의존: P3.

변경 위치: 향후 `src/environments/`, `src/examples/`, 환경 설정 UI와 단위·통합 테스트.

1. stream 청크 분할·합치기·방향별 지연·정상 EOF·연결 실패를 구현한다.
2. datagram 방향별 지연·지연 변동·손실·중복·특정 전송 손실과 seed를 구현하고 환경 판정·사본 원인 ID를 기록한다.
3. 무조건 데이터/ACK를 수신하면 상위에 전달하는 예제 대신 명시적인 순서 번호·대기 패킷·ACK 검사·타이머·중복 제거를 가진 단순 전송 프로토콜을 정의한다.
4. 초기 송신 후 재시도 상한까지 실패하면 참여자가 Failed에 도달하도록 한다. 최초 송신 횟수와 재시도 횟수를 구분한다.

검증: Ping/Pong 청크 크기 변화 후 결과 보존, 데이터 손실/ACK 손실/중복/순서 역전, 늦은 ACK, 재전송 데이터의 상위 중복 전달 억제, 모든 전송 손실 시 유한 실패, 같은 seed 재현, 스트림의 바이트 순서·중복 없는 전달 불변식.

완료 조건: 같은 정의를 정상·손실 환경에서 실행해 결과 차이와 원인을 UI·기록에서 확인한다. 관찰 기간 전체의 상위 전달 데이터와 횟수를 검사한다.

### P5 — 기존 프로토콜 예제

의존: P4.

변경 위치: 향후 `src/codecs/`, `src/examples/`, 라이브러리·예제 설명 UI와 fixture.

1. 설계 범위의 HTTP/1.1 코덱과 GET·POST 정상/헤더 오류/본문 길이·분할 수신/응답 지연 예제를 구현한다.
2. 정상 SYN·SYN-ACK·ACK와 양쪽 상태·seq/ack를 보여주는 TCP 연결 수립 개념 모델을 구현한다. 전체 TCP 데이터 전송이나 재전송 동작으로 설명하지 않는다.
3. 예제 원본·출처·버전·지원/생략 항목을 제공하고 수정 시 사용자 정의 사본을 만든다.

검증: HTTP Content-Length의 UTF-8 바이트 길이·잘못된 헤더·미완성 본문·지원하지 않는 형식, TCP SYN의 순서 번호 소비와 올바른 ACK 값·상태, 원본을 수정하지 않는 사본 생성, 서비스 불일치 실행 차단.

완료 조건: 라이브러리의 모든 예제가 화면과 엔진 fixture에서 같은 결과를 내고 제한된 표준 지원 범위를 명확하게 표시한다.

### P6 — 저장·bundle·snapshot 재생

의존: P5. snapshot·runId 계약은 P2부터 유지한다.

변경 위치: 향후 `src/persistence/`, `src/application/`, 저장·가져오기·내보내기·기록 재생 UI.

1. 지원 브라우저·저장량·원자적 갱신을 기준으로 저장 수단을 선택하고 결정 로그에 남긴다.
2. 실험·초안·예제 사본·불변 run snapshot과 결과를 보존하고 저장 실패 시 미저장 표시와 메모리 초안을 유지한다.
3. schemaVersion이 있는 자급적인 bundle을 내보낸다. 가져오기는 staging 검증 후 적용하며 ID 충돌 시 새 사본을 만든다.
4. 과거 기록 선택과 새 실행을 분리한다. 저장한 snapshot으로 재실행하고 원본 편집·삭제가 과거 결과에 영향을 주지 않게 한다.

검증: 새로고침 후 복원, 유효하지 않은 초안 저장 후 실행 차단, 왕복 export/import, ID 충돌, 손상/지원하지 않는 버전/용량 초과 bundle, 저장 quota 실패, 참조 중 정의 삭제, 과거 run 보존과 현재 초안 차이 표시.

완료 조건: 별도 세션에서도 실험을 재개하고 당시 snapshot과 의미적 기록을 재현한다. 저장 실패를 성공 표시로 숨기지 않는다.

### P7 — v1 전체 검증과 문서 정리

의존: P6.

변경 위치: 향후 `tests/e2e/`, 필요한 CI 설정, UI 응답성 보완, 현재 구조·개발 문서와 이 계획.

1. 실제 브라우저에서 새 실험 작성 → 환경 변경 → 실행 → 원인 확인 → 저장/복원 전체 흐름을 검증한다. 정적 mock이나 코어 테스트로 대체하지 않는다.
2. 지원 브라우저와 viewport를 확정하고 키보드 사용·초점 이동·오류 안내·패널 재배치를 확인한다.
3. 10,000 이벤트와 1 MiB 기본 상한 fixture에서 브라우저 응답성을 측정한다. 응답성 기준을 수치로 결정한 뒤 통과 여부를 기록한다. 필요하면 엔진 batch 처리/worker와 기록 표시 범위를 조정하고 결정성·run fencing을 재검증한다.
4. 타입 검사·단위/통합/E2E·문서 검사·빌드를 실제 실행하고 필요한 CI에 같은 명령을 구성한다. 원격 CI 실행 여부는 별도로 기록한다.
5. 실제 만들어진 경로·명령·지원 범위를 구조/개발 문서에 반영한다. 미실행 검증과 필수 미완료 항목이 있으면 계획을 완료로 표시하지 않는다.

완료 조건: 아래 수용 행렬이 충족되고 결과·한계가 기록된다. 이 계획을 Completed로 바꿔 같은 파일명으로 completed에 옮기며 목록과 링크를 갱신한다. 배포는 별도 요청 범위다.

## Validation and Acceptance

### 구성된 검증 명령

P0에서 아래 명령을 저장소 루트 기준으로 구성했다. 정확한 도구 버전·설치·격리는 [개발 기준](../../development.md)을 따른다. 현재 테스트는 P0 범위이며 이 명령의 존재가 이후 기능의 구현 완료를 뜻하지 않는다.

| 명령 | 관찰할 결과 |
| --- | --- |
| `pnpm install --frozen-lockfile` | 이미 합의·생성된 lockfile로 재현 가능하게 설치 |
| `pnpm typecheck` | 새 TypeScript 파일 strict 검사 |
| `pnpm test` | 코어 단위·통합 fixture가 실제 수집·실행되고 통과 |
| `pnpm test:e2e` | 현재 P0 빌드 화면 smoke test. 사용자 편집·실행·저장 흐름은 이후 단계에서 추가 |
| `pnpm check:docs` | 실제·제안 구분, 로컬 링크·앵커·양식 검사 |
| `pnpm build` | 선택한 웹 도구의 배포용 빌드 성공 |
| `pnpm check` | 합의된 타입·테스트·문서·빌드 필수 검사 집계 |
| `git diff --check` | 추적된 변경의 공백 오류 없음. untracked 파일은 별도 검사 |

포맷·정적 분석은 `pnpm format:check`와 `pnpm lint`, Node 테스트는 내장 runner, 브라우저 검증은 Playwright Chromium을 사용한다. `pnpm test:e2e`가 빌드를 포함한다. production dependency는 추가 전 확인하고, 이 표를 새 패키지 설치 승인으로 취급하지 않는다.

## Idempotence and Recovery

각 단계 시작 전에 브랜치·변경·실제 경로·완료 체크를 다시 확인한다. 구현된 단계의 테스트와 현재 코드를 대조해 이어가며 scaffold·정의·예제 ID·의존성·데이터를 중복 생성하지 않는다. 사용자 변경을 reset·clean·stash하지 않는다.

실행 snapshot·schemaVersion·engineVersion을 처음부터 유지한다. import는 검증 후 사본으로 적용하고 기존 데이터 복구 수단 없이 포맷을 변경하지 않는다. 실패한 실행을 정상 완료로 덮어쓰지 않는다. 새 run은 이전 상태·타이머·callback을 재사용하지 않는다. 저장 실패 시 메모리 초안과 마지막 저장본을 보존한다.

커밋을 요청받으면 단계의 검사 완료 범위에 맞춰 conventional commit을 사용한다. 이 계획은 강제 push·배포·외부 연결을 승인하지 않는다. 과거 로컬 검증을 CI나 실제 네트워크 검증으로 재사용하지 않는다.

## Interfaces and Dependencies

프로토콜 정의, 서비스 포트, 환경 정의, 실행 snapshot, 이벤트 기록, 기대 조건, 저장 bundle이 내부 계약이다. 포맷 변경 시 버전을 올리고 호환성과 재생 범위를 기록한다. 실제 외부 API·소켓·서버와 production 데이터는 사용하지 않는다.

P0에서 사용자가 승인한 React·React DOM을 production dependency로 추가했다. 빌드·타입·포맷·테스트·문서 검사 도구는 devDependency이며 package.json·lockfile에 버전을 고정했다. 로컬 저장 기술은 P6에서 결정한다. 이후 신규 production dependency도 사용자 확인 후 추가한다.
